# Sources: what the platform docs said, and what this kit does with it

The Retell pages below were read on **2026-11-01** (the date of this build). The Vapi pages were read again on **2026-11-02**, this time as the raw Markdown version of each page (append `.md` to the URL), because the 2026-11-01 reading went through a summarising fetch tool and the adapter needed exact field names. Vendor docs change; re-read them before a real deployment.

**How they were read:** the Retell pages through a fetch tool that returns a summary of each page, not the raw page. Where a page has a Markdown version (the `.md` URLs below) that was fetched too, because it keeps the example JSON. The Vapi pages as raw Markdown. Anything a page could not show is listed as *not confirmed* rather than filled in. No account on either platform was used, and no request was ever sent to the Retell or Vapi APIs; reading their public documentation pages is all that was done.

## Retell AI

| Topic | URL | What the page said (relevant facts only) |
|---|---|---|
| Webhook signature | https://docs.retellai.com/features/secure-webhook | Header `X-Retell-Signature`, value `v={timestamp},d={hex_digest}`, parsed with `v=(\d+),d=(.*)`. `v` is a Unix timestamp **in milliseconds**. `d` is HMAC-SHA256, hex, of **the raw request body with the timestamp string appended** (`raw_body + timestamp`), keyed with the Retell API key (only the key that has a "webhook badge" next to it). Reject if the timestamp is more than **5 minutes** from now (the Go sample does `abs(now - timestamp) > 5*60*1000` in ms). Compare in constant time. Use the raw body, never a re-serialised copy. Node/Python SDKs expose `Retell.verify(rawBody, apiKey, signature)`. Optional: allow-list Retell's IP `100.20.5.228`. |
| Webhook events and payloads | https://docs.retellai.com/features/webhook-overview (and the `.md` version) | Voice events: `call_started`, `call_ended`, `call_analyzed`, `transcript_updated`, `transfer_started`, `transfer_bridged`, `transfer_cancelled`, `transfer_ended`. Body is `{ "event": ..., "call": {...} }`. `call_ended` carries "all fields from the call object except `call_analysis`"; the sample shows `call_type`, `from_number`, `to_number`, `direction`, `call_id`, `agent_id`, `call_status`, `metadata`, `retell_llm_dynamic_variables`, `start_timestamp`, `end_timestamp`, `disconnection_reason`, `transcript`, `transcript_object`, `transcript_with_tool_calls`, `data_storage_setting`. `metadata` and `retell_llm_dynamic_variables` are omitted when not provided. `call_analyzed` is "full call data including `call_analysis` object" (the page has no sample for it). Retell expects a 2xx and no body; **timeout 10 s; retried up to 3 times** if no 2xx; lifecycle events fire at most once per call; the page recommends idempotent handling keyed on event + `call_id`. |
| Call object fields | https://docs.retellai.com/api-references/get-call | Phone call: `call_type` (`phone_call`), `from_number`, `to_number`, `direction` (`inbound`/`outbound`), `call_id`, `agent_id`, `call_status` (`registered`, `not_connected`, `ongoing`, `ended`, `error`), `start_timestamp`/`end_timestamp` (ms since epoch), `duration_ms`, `transcript` (string), `transcript_object` (items: `role` = `agent`/`user`/`transfer_target`, `content`, `words`), `disconnection_reason` (large enum incl. `user_hangup`, `agent_hangup`, `call_transfer`, `voicemail_reached`, `inactivity`, `max_duration_reached`, `error_*`), `transfer_destination`, `call_analysis` = `{ call_summary, in_voicemail, user_sentiment (Negative/Positive/Neutral/Unknown), call_successful, custom_analysis_data }`, `call_cost`. |
| Custom function (tool) | https://docs.retellai.com/build/single-multi-prompt/custom-function (and the `.md` version) | POST by default (GET, PUT, PATCH, DELETE also; JSON body only for POST/PUT/PATCH). URL must be public (localhost, private ranges and cloud-metadata addresses are blocked). Request body: `{ "name": <function name>, "args": {...}, "call": {...call context incl. call_id, transcript so far...} }`. Header `X-Retell-Signature` is sent. "Payload: args only" sends just the args object, with no `name`, `call` or `args` wrapper (so no `call_id`: this kit does not use that mode). Timeout 1000 to 600000 ms (default 120000). `max_retry` 0 to 5, default 0; retries fire on network errors, timeouts and 4xx/5xx; only the last attempt reaches the agent; "retries can cause duplicate processing, so use them only with idempotent endpoints". Any 2xx is success; the body can be a string or JSON and is converted to a string for the LLM; capped at 15,000 characters by default. A property in `parameters` with a `description` is filled by the LLM. Interrupted calls still run to the timeout. |
| Create Retell LLM (config shape) | https://docs.retellai.com/api-references/create-retell-llm | `general_prompt`, `general_tools[]`, `begin_message`, `start_speaker`, `starting_state`, `states`, `default_dynamic_variables`, `model_config` (`type`: `cascading`/`s2s`/`duplex`; `model` and `model_temperature` are marked deprecated). Tool `type` values: `end_call`, `transfer_call`, `agent_swap`, `press_digit`, `send_sms`, `custom`, `code`, `extract_dynamic_variable`, `bridge_transfer`, `cancel_transfer`, `mcp`, `integration_app`. `custom` requires `type`, `name`, `url`; optional `description`, `method`, `headers`, `query_params`, `parameters`, `speak_during_execution`, `speak_after_execution`, `execution_message_description`, `execution_message_type` (`prompt`/`static_text`), `timeout_ms`, `max_retry`, `args_at_root`, `response_variables`, `execution_status_variable`, `enable_typing_sound`. `transfer_call` requires `type`, `name`, `transfer_destination` (`{type:"predefined", number, extension}` or `{type:"inferred", prompt}`), `transfer_option` (`cold_transfer`, `warm_transfer` or `agentic_warm_transfer`, each with its own `type`). `end_call` requires `type`, `name`. |
| Create Retell LLM, tool fields (second look, same date) | https://docs.retellai.com/api-references/create-retell-llm | Fields per tool type as the page lists them. `transfer_call`: `type`, `name`, `description` (optional), `transfer_destination`, `ignore_e164_validation`, `custom_sip_headers`, `transfer_option`, `speak_during_execution`, `execution_message_description`, `execution_message_type`. `end_call`: `type`, `name`, `description` (optional), `custom_sip_headers`, `speak_during_execution`, `execution_message_description`, `execution_message_type`. `custom` additionally lists `parameter_type`. `transfer_option` with `type: "cold_transfer"` requires only `type`; optional `show_transferee_as_caller`, `cold_transfer_mode` (`sip_refer` or `sip_invite`, default `sip_invite`), `on_hold_music`, `custom_on_hold_music_asset_id`, `transfer_ring_duration_ms`. The kit sets only `type` there. |
| Create Agent (config shape) | https://docs.retellai.com/api-references/create-agent | Required: `response_engine` (`{type:"retell-llm", llm_id, version}`) and `voice_id`. Optional: `agent_name`, `language` (default `en-US`), `timezone` (IANA, default `America/Los_Angeles`), `webhook_url`, `webhook_events` (default `call_started`, `call_ended`, `call_analyzed`), `webhook_timeout_ms` (default 10000), `begin_message_delay_ms`, `end_call_after_silence_ms` (min 10000), `max_call_duration_ms` (60000 to 7200000), `interruption_sensitivity`, `post_call_analysis_data[]` (custom: `type` string/enum/boolean/number + `name` + `description`; presets: `{type:"system-presets", name: call_summary|call_successful|user_sentiment}`), `post_call_analysis_model`. |
| Transfer call (behaviour) | https://docs.retellai.com/build/single-multi-prompt/transfer-call | Target: E.164 number, SIP URI or a dynamic variable. Cold, warm and agentic-warm transfers. Phone calls only, not web calls. After a transfer the AI fee stops; telephony continues. |
| Phone numbers | https://docs.retellai.com/api-references/create-phone-number | Agents are attached with `inbound_agents` / `outbound_agents` (arrays of `{agent_id, agent_version, weight}`), **not** `inbound_agent_id`. ## Vapi (read again on 2026-11-02, as raw Markdown)

The adapter (`src/vapi.ts`, routes in `src/server.ts`) and the run script (`scripts/vapi-run.mjs`) were written from these pages. The notes that stood here on 2026-11-01 came from a summarising fetch and are replaced. Nothing below has been seen from a real Vapi account.

| Topic | URL | What the page said (relevant facts only) |
|---|---|---|
| Server messages | https://docs.vapi.ai/server-url , https://docs.vapi.ai/server-url/events | The server URL receives `{ "message": { "type": ..., ... } }`. Types include `tool-calls`, `end-of-call-report`, `status-update`, `transfer-destination-request`, `assistant-request`, `chat.created`, `chat.deleted`. A message can carry `assistant`, `customer`, `call` and `chat`. |
| Tool-call request | https://docs.vapi.ai/tools/custom-tools , https://docs.vapi.ai/api-reference/webhooks/server-message | `message.type` is `tool-calls`. `message.toolCallList[]` holds `{ id, type: "function", function: { name, arguments } }`; the guide's example shows `arguments` as an object. `message.toolWithToolCallList[]` repeats each tool definition with its `toolCall`. In the API reference only `toolWithToolCallList` and `toolCallList` are required; `type`, `timestamp`, `artifact`, `assistant`, `customer`, `call`, `chat` and `phoneNumber` are optional. |
| Tool-call response | same two pages | HTTP 200 with `{ "results": [ { "toolCallId", "result" } ] }`. `result` must be a flat string, not an object, array or multi-line value. On failure, `error` (also a flat string) goes in its place, one of the two per `toolCallId`; Vapi decides whether to speak the failed-request message from the presence of `error`. **Any status other than 200 is ignored completely** and the assistant reports "no result returned". The API reference's `ToolCallResult` lists `name` (required), `toolCallId` (required), `result`, `error`, `message`, `metadata`; the guide's example leaves `name` out. This kit sends `name` as well. |
| Server authentication | https://docs.vapi.ai/server-url/server-authentication | Credentials are made in the dashboard and referenced by `credentialId`: Bearer Token (header name configurable, default `Authorization`, optional `Bearer ` prefix), OAuth 2.0 client credentials, HMAC (secret key, algorithm, signature header, optional timestamp header, payload format, signature encoding). A Bearer Token credential with header `X-Vapi-Secret` and no prefix reproduces the older inline `secret` field ("legacy X-Vapi-Secret support"). The HMAC payload format `{timestamp}.{body}` appears only in the text that describes a screenshot of the form, not in the prose. Vapi attaches an org credential only to server URLs that come from saved resources (assistant, phone number, tool, Server Configuration), not to a server URL supplied inline in a request (a transient assistant, `assistantOverrides`); for those the page says to put the credential in the request's `server.headers`. The page says this applies to organizations created on or after 2026-09-23 (UTC) and is rolling out in phases to older ones. |
| `Server` object | https://docs.vapi.ai/api-reference/tools/create , https://docs.vapi.ai/api-reference/assistants/create | `url`, `timeoutSeconds` (default 20), `credentialId`, `headers` (static HTTP headers), `staticIpAddressesEnabled`, `encryptedPaths`, `backoffPlan` (no retry by default). There is **no `secret` field** in the current schema; the only appearance of `secret` is the "before" example in the migration notes on the authentication page. |
| `end-of-call-report` | https://docs.vapi.ai/api-reference/webhooks/server-message , https://docs.vapi.ai/server-url/events | `type`, `endedReason` (a long enum), `artifact` (transcript, messages, recording), `analysis` (`summary`, `structuredData`, `successEvaluation` as a string); optional `cost`, `costs[]`, `destination` (when the call was forwarded), `call`, `customer`, `chat`, `startedAt` and `endedAt` (ISO 8601 strings). No duration field. Described as sent "when the call ends and post-processing is complete". |
| Create assistant, create tool, delete | https://docs.vapi.ai/api-reference/assistants/create , https://docs.vapi.ai/api-reference/tools/create , https://docs.vapi.ai/api-reference/assistants/delete , https://docs.vapi.ai/api-reference/tools/delete | Assistant: `name`, `model` (`provider: "openai"`, `model`, `messages[]` of `{role, content}`, `toolIds[]`, `tools[]`, `temperature`, `maxTokens`), `server`, `serverMessages` (default includes `tool-calls` and `end-of-call-report`). Function tool: `type: "function"`, `function: { name, description, parameters }`, `server`, `messages`, `async`. `DELETE /assistant/{id}` and `DELETE /tool/{id}`. The OpenAI model list includes `gpt-4.1-mini`. |
| Chat API | https://docs.vapi.ai/api-reference/chats/create , https://docs.vapi.ai/api-reference/chats/get , https://docs.vapi.ai/api-reference/chats/delete , https://docs.vapi.ai/chat/quickstart , https://docs.vapi.ai/chat/non-streaming , https://docs.vapi.ai/chat/session-management | `POST https://api.vapi.ai/chat` with `Authorization: Bearer <private key>`. Body: `input` (required; a string or an array of messages), `assistantId` (or `assistant`, `squadId`, `squad`), `assistantOverrides` ("only variable substitution is supported in chat contexts"), `name`, `previousChatId` or `sessionId` (mutually exclusive), `stream` (default false), `transport` (SMS). Output items are system, user, assistant (`content`, `tool_calls[]`), tool (`tool_call_id`, `content`) or developer messages. The non-streaming guide reads `output[0].content`. `GET /chat/{id}` and `DELETE /chat/{id}` exist. |
| Variables | https://docs.vapi.ai/assistants/dynamic-variables | `{{name}}` in prompts; values passed as `assistantOverrides.variableValues`, not persisted. | Call forwarding | https://docs.vapi.ai/call-forwarding | `transferCall` tool JSON: `{ "type": "transferCall", "destinations": [ { "type": "number", "number": "+14155550100", "message": "...", "description": "...", "transferPlan": { "mode": "blind-transfer" } } ] }`. **What changed against the 2026-11-01 notes.** The authentication page is read the same way, but the `X-Vapi-Secret` header is now labelled legacy and the `Server` schema has no `secret` field, so the snippet and the run script carry the secret in `server.headers`. The layout of `end-of-call-report` (`analysis.summary`, `startedAt`, `endedAt`) is documented after all, which the old notes said it was not; a duration field still is not. The response example in the guide has no `name`; the API reference marks it required. The Chat API shapes are new. The HMAC signed string is still only in screenshot text.

## Not confirmed from the docs (and what the kit does about it)

1. **Does the tool-call signature use the same `v=...,d=...` scheme as webhooks?** The webhook page documents the scheme in detail. The custom-function page only says `X-Retell-Signature` is "an HMAC-SHA256 signature of the request body", shows `Retell.verify(rawBody, apiKey, signature)`, and says to pass an empty string for GET/DELETE. Both pages use the same SDK function, so the kit applies the webhook scheme to tool calls too. If a real tool call fails verification, this is the first thing to check.
2. **Is a retried request re-signed (new timestamp) or re-sent with the same header?** Not stated. The kit's replay guard rejects an identical signature seen before (HTTP 409), and the shipped config sets `max_retry` to 0. If you raise `max_retry`, set `REPLAY_POLICY=cached` (see README).
3. **Do 4xx/5xx responses to a tool call show their body to the agent?** Not stated; the docs only say retries fire on those statuses and "the agent receives the error" on a timeout. So the kit answers *business* errors (slot taken, bad date, unknown service) with HTTP 200 and `ok:false` plus a spoken-style `message`, and uses 4xx/5xx only for transport and authentication problems.
4. **The JSON key for choosing the LLM.** `model` is deprecated in favour of `model_config`, but the page does not spell out what goes in `model_config.primary`. The shipped config does not choose a model; pick one in the dashboard.
5. **A sample `call_analyzed` payload and a sample `call_ended` with `duration_ms`.** Neither is shown on the webhook page (the field is documented on the call object). The kit reads `duration_ms` if present and otherwise computes it from the two timestamps.
6. **Whether a dynamic variable can be used as the `transfer_call` number inside the JSON config.** The dashboard text allows it; the API page shows `predefined` with `number`. The kit uses two fixed-number transfer tools.
7. **Vapi.** The 2026-11-02 reading settled the layout of `end-of-call-report` (`analysis.summary`, `startedAt`, `endedAt`) and the tool-call and chat shapes on paper. What it could not settle is listed as V1 to V11 below. An adapter exists (`src/vapi.ts`); it is tested against the documented shapes only and has never received a real Vapi request. The HMAC option is not implemented, because the signed string is described only in screenshot text.
8. **Pricing pages show no effective date**, and some numbers conflict inside the page. See `COSTS.md`.

### Vapi: not confirmed until a real request is seen (V1 to V11)

V1. **Whether a Chat API conversation makes Vapi call the tool server at all, and what that `tool-calls` message carries.** The server-message schema has an optional `chat` field, which suggests it does; no example shows it. The adapter takes the call id from `message.call.id` and falls back to `message.chat.id`, and the caller's number from `call.customer.number` or `message.customer.number`. If every `POST /chat` is a new chat with a new id, call-scoped idempotency is per chat, not per conversation.
V2. **Whether `server.headers` on a saved tool is sent exactly as written** (name and case). The adapter accepts `X-Vapi-Secret` or `Authorization: Bearer`; a 401 in the server log means neither arrived.
V3. **Whether `function.arguments` arrives as an object (the guides) or as a JSON string.** The adapter accepts both.
V4. **Whether Vapi sends `end-of-call-report` for a text chat at all.** The page says "when the call ends"; the chat events listed are `chat.created` and `chat.deleted`. If it does not, `/vapi/webhook` stays tested against the documented layout only.
V5. **Whether tool calls and tool results appear in the chat answer** (`output[]` or `messages[]`). The run script reports a tool check as "not observable" when they do not, and the server's shape log is then the only evidence.
V6. **Whether one `POST /chat` finishes a whole tool round** (the model asks, the tool server answers, the model replies) or returns after the request.
V7. **The credential rule for older organizations.** The page describes `server.headers` as the way to authenticate a URL supplied inline, and a saved tool keeps its credentials; it does not say how a static header on a saved tool behaves for an organization created before 2026-09-23.
V8. **What a billing or credit failure looks like.** The run script stops on HTTP 402 or on credit or billing wording in a 4xx body; the real status and text are unknown.
V9. **Whether `gpt-4.1-mini` is available on the account, and what `maxTokens` default applies** (the script sets 500).
V10. **The HMAC signed string.** Not implemented.
V11. **Whether a chat answer reports `cost` or `costs[]`.** The run script records them if present and says "not reported" if not.
